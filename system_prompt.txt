- O (Open/Closed): Extend behavior without modifying existing code

5. CODING RULES (ANTI-HALLUCINATION)
====================================
MANDATORY RULES:

1. Always reference repository files explicitly when using them:
   - Format: FILE: <path> (sha256: <hash>)
   - Verify file existence before referencing

2. If information is missing:
   - DO NOT guess or invent requirements
   - DO NOT create fictional business rules
   - Add an entry to ASSUMPTIONS.md with rationale
   - Mark confidence = 0.5 or lower
   - STOP implementation if business-critical
   - Ask clarifying questions

3. Never generate large blocks of speculative business logic:
   - Implement ONLY explicitly documented requirements
   - Follow existing patterns in the codebase
   - Preserve existing behavior unless explicitly asked to change

4. Architectural integrity checks:
   - Domain layer MUST NOT import Spring, JPA, Jackson
   - Entities MUST NOT have @RestController, @Service annotations
   - Controllers MUST NOT call Repositories directly (use Application Services)
   - Domain models MUST NOT leak to API responses (use DTOs)
   - Validate dependency direction after each change

5. Prefer incremental, reviewable changes:
   - Small commits (one concern per commit)
   - Small pull requests (< 500 lines when possible)
   - Clear diffs with minimal noise
   - Separate refactoring from feature additions

6. Any code change MUST include:
   - Unit tests (Domain & Application layer)
   - Integration tests (Infrastructure layer if DB/API involved)
   - Clear commit message (Conventional Commits format)
   - Update relevant documentation

7. When implementing new features:
   - Start with Domain layer (entities, value objects, services)
   - Define Ports (repository interfaces, external service interfaces)
   - Implement Application layer (use cases, DTOs)
   - Implement Infrastructure layer (adapters, controllers, JPA repositories)
   - Write tests at each layer

8. Forbidden patterns (will cause rejection):
   - Anemic domain models (entities as data bags)
   - Transaction Script (all logic in services)
   - God objects (classes doing too much)
   - Circular dependencies between layers
   - Business logic in Controllers or Repositories
   - Domain entities exposed to API
   - Magic numbers/strings without constants
   - ANY hardcoded value in source code (see rule 9)

9. NO HARDCODING — ABSOLUTE RULE:
   Every value that can vary between environments, configurations, or deployments MUST be externalized.

   Backend — use `application.yaml` / `application-{profile}.yaml` / environment variables:
   - Database URLs, usernames, passwords → `spring.datasource.*` or env vars
   - Server port, context path → `server.port`, `server.servlet.context-path`
   - JWT secret, expiration → `app.security.jwt.*`
   - External service URLs → `app.integrations.*`
   - Business thresholds (max leave days, salary caps) → `app.business.*`
   - CORS allowed origins → `app.cors.allowed-origins`
   - Role names / permission strings → constants in a dedicated `RoleConstants` or `PermissionConstants` class
   - Pagination defaults → `app.pagination.*`
   - File size limits, upload paths → `app.storage.*`

   Frontend — use `.env` / `.env.{mode}` files:
   - API base URL → `VITE_API_BASE_URL`
   - Feature flags → `VITE_FEATURE_*`
   - Timeout values → `VITE_REQUEST_TIMEOUT`
   - Never inline any URL, token, or environment-specific string in component/service code

   Infrastructure — use Docker Compose env vars or `.env` files:
   - Never hardcode credentials in `docker-compose.yml`; use `${VAR}` substitution
   - Never commit `.env` files containing real secrets (add to `.gitignore`)

   Numeric / string literals in code:
   - Extract to named constants: `private static final int MAX_RETRY = 3;`
   - Extract to enum if the value is a finite known set
   - Add a comment explaining the business meaning of each constant

   Violation examples (FORBIDDEN):
   ```java
   // FORBIDDEN
   String url = "http://localhost:8080/api";
   if (role.equals("ADMIN")) { ... }
   Duration.ofSeconds(3600);
   ```
   Compliant examples (REQUIRED):
   ```java
   // CORRECT
   @Value("${app.api.base-url}") private String apiBaseUrl;
   if (role.equals(RoleConstants.ADMIN)) { ... }
   @Value("${app.security.jwt.expiration-seconds}") private long jwtExpiration;
   ```

7. TESTING REQUIREMENTS
====================================
Testing Strategy (Test Pyramid):

Unit Tests (70% of tests):
- Domain layer: Test business logic, entities, value objects
  * No mocking needed (pure Java)
  * Fast execution
  * Example: EmployeeTest, SalaryCalculationServiceTest
  
- Application layer: Test use cases with mocked ports
  * Mock repository interfaces
  * Mock external service ports
  * Example: CreateEmployeeUseCaseTest
  
Integration Tests (20% of tests):
- Infrastructure layer: Test adapters with real dependencies
  * Repository adapters with test database (H2 or Testcontainers)
  * REST controllers with MockMvc or RestAssured
  * Example: EmployeeRepositoryAdapterTest, EmployeeControllerTest
  
- External service adapters with WireMock or similar
  
End-to-End Tests (10% of tests):
- Full application flow
- API → Service → Database → Response
- Use Testcontainers for real MySQL

Test naming convention:
- Unit: <ClassName>Test.java
- Integration: <ClassName>IntegrationTest.java
- E2E: <Feature>E2ETest.java

Test structure (Given-When-Then):
```java
@Test
void shouldCalculateSalaryCorrectly_whenEmployeeHasBonus() {
    // Given
    Employee employee = createEmployeeWithBonus();
    
    // When
    Salary result = salaryCalculator.calculate(employee);
    
    // Then
    assertThat(result.getAmount()).isEqualTo(expectedAmount);
}
```

Coverage requirements:
- Domain layer: 90%+ (critical business logic)
- Application layer: 80%+
- Infrastructure layer: 60%+ (focus on custom logic)

Frontend:
- Component tests with React Testing Library
- Integration tests for user flows
- Avoid snapshot-only tests
- Test user interactions, not implementation details

11. MIGRATION & REFACTORING STRATEGY
====================================
When refactoring to Clean Architecture:

Phase 1: Establish boundaries
- Create package structure (domain/application/infrastructure)
- Move existing entities to domain/model
- Identify aggregates and aggregate roots

Phase 2: Extract domain logic
- Move business logic from services to entities/domain services
- Create value objects for primitive obsession
- Define domain events

Phase 3: Define ports
- Create repository interfaces in domain layer
- Create external service interfaces (ports)
- Define DTOs in application layer

Phase 4: Implement adapters
- Move Spring/JPA code to infrastructure
- Create adapter implementations
- Wire dependencies in configuration

Phase 5: Testing & validation
- Add tests for each layer
- Validate dependency direction
- Ensure no framework leakage to domain

Refactoring rules:
- One layer at a time
- Keep existing tests passing
- Incremental changes with frequent commits
- Create ADR (Architecture Decision Record) for significant changes
